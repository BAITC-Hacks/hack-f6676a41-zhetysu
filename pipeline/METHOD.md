# Метод ядра анализа — «Граф денег»

Материал для README и для защиты перед жюри. Все числа в таблицах порогов —
не константы в коде, а квантили распределений, посчитанные на прогоне;
машинно-читаемая копия лежит в `out/thresholds.json`.

Запуск:

```bash
.venv/bin/python -m pipeline.run --data case/data --out out
```

Один запуск, без ручных шагов, ~9 секунд на предоставленном объёме
(лимит ТЗ — 300 секунд). На выходе: `out/nodes_roles.csv` (2248 строк),
`out/clusters.csv`, `out/top_nodes.csv` (30 строк), `out/graph.json`,
плюс `out/thresholds.json` и `out/censoring_report.json` — обоснование порогов
и отчёт модели обрыва обхода.

## Конвейер

```
parquet (edges, nodes, transactions)
  → проверки консистентности (edges == transactions, gid уникален)
  → направленный взвешенный граф (DiGraph, вес = sum_kzt)
  → метрики узла: структура, деньги, время
  → модель обрыва обхода → terminal_status, terminal_p
  → роли по формальным правилам (пороги = квантили)
  → coordinator: второй проход по иерархии плательщиков
  → кластеры (Louvain на неориентированной проекции) + гипотезы
  → priority_score (6 взвешенных компонент) + топ-30 с обоснованием
  → четыре файла в out/
```

## Пороги (считаются на прогоне)

| Порог | Правило | Значение на этих данных |
|---|---|---|
| `in_deg_consolidator` | квантиль 0.975 распределения `in_deg` | 4 плательщика |
| `out_deg_distributor` | квантиль 0.975 распределения `out_deg` | 11 получателей |
| `materiality_kzt` | медиана `in_kzt` среди узлов с поступлениями | 50 000 KZT |
| `in_money_high_kzt` | квантиль 0.95 распределения `in_kzt` | 613 779 KZT |
| `betweenness_high` | квантиль 0.99 `betweenness` | верхний 1% |
| `retention_pass_through` | квантиль 0.20 `pass_through` среди передающих дальше | 0.26 |
| `transit_pass_through` | коридор ±20% вокруг единицы | 0.8 … 1.2 |
| `terminal_p_min` | смысловое решение (см. ниже) | 0.70 |

Ядро системы — три зоны по доле пропуска `pass_through = out_kzt / in_kzt`:
прошло почти всё (транзит), почти всё осело (конечный получатель), между
(смешанный профиль — роль не утверждаем). Число плательщиков и получателей
отделяет сбор от веерной рассылки.

## Правила ролей

Применяются в фиксированном порядке, первое сработавшее побеждает. `rule_id`
каждого узла записан в `nodes_roles.csv` и в `graph.json` — по любому gid видно,
каким именно правилом присвоена роль.

| Правило | Условие | Узлов |
|---|---|---|
| R0 `peripheral` | нет ни одного ребра в выгрузке | 19 |
| R1 `distributor` | `out_deg >= 11` | 54 |
| R2 `consolidator` | `in_deg >= 4` и (`out_deg <= max(2, in_deg/2)` или `pass_through <= 0.5`) | 43 |
| R3a `transit` | `0.8 <= pass_through <= 1.2` | 67 |
| R3b `transit` | `pass_through > 1.2` — отдал больше, чем получил по данным | 249 |
| R3c `transit` | seed с исходящими: роль по исходящему профилю | 40 |
| R3d `transit` | ≥60% исходящих в пределах 2 суток после поступления | 25 |
| R4a `terminal` | исходящих нет, и они проверены обходом (`depth <= 3`) | 1069 |
| R4b `terminal` | исходящие есть, но дальше уходит ≤26% — сумма осела | 105 |
| R4c `terminal` | обрезан 4-м коленом, `terminal_p >= 0.70` | 86 |
| R5 `peripheral` | смешанный профиль ниже всех порогов | 464 |
| R6 `coordinator` | иерархия + деньги (второй проход, см. ниже) | 27 |

`coordinator` — три условия одновременно: (1) узел получает минимум от двух
плательщиков, которые сами собирают деньги от 4+ плательщиков, либо напрямую
минимум от двух seed; (2) поступления в верхних 5% распределения `in_kzt`;
(3) узел не seed — 81 нижнее звено следствию уже известно, и входящие суммы у
них занижены по устройству выгрузки. Правило намеренно узкое: 27 кандидатов из
2248 — это список на проверку, а не вывод о роли в группе.

`role_score` — уверенность в роли, а не важность узла: насколько узел ушёл за
порог своего правила (для `terminal` по обрезанным узлам — ровно вероятность по
модели, без округления вверх; для seed ограничена 0.55, потому что их приток не
наблюдаем).

## Ловушка 1: обрыв обхода на 4-м колене

444 узла имеют `depth = 4` и `out_deg = 0`. Наивное правило
«`out_deg == 0` ⇒ конечный получатель» дало бы 444 ложных вывода.

Что наблюдаемо:

| Узел | Исходящие запрашивались обходом? | Вывод |
|---|---|---|
| `depth <= 3`, `out_deg = 0` | да, и их не нашлось | конечный получатель подтверждён данными |
| `depth <= 3`, `out_deg >= 1` | да | передаёт дальше |
| `depth = 4`, `out_deg = 0` | нет, обход остановлен | неизвестно, нужна оценка |

Метод: на коленах 1–3 факт «есть ли исходящие» наблюдаем, поэтому там можно
измерить связь этого факта с ВХОДЯЩИМ профилем узла и профилем его
плательщиков — а и то, и другое у 4-го колена видно полностью (его плательщики
лежат на 3-м колене и измерены). Логистическая регрессия на 10 интерпретируемых
признаках обучается на 1723 узлах колен 1–3 и применяется к 444 обрезанным,
давая `terminal_p`.

Признаки: сумма и число поступлений, число плательщиков, средний размер
поступления, концентрация входящих, сколько дней до конца периода оставалось
после последнего поступления, широта рассылки плательщиков (макс. и средняя),
доля денег от веерных плательщиков, число плательщиков-seed.

Проверка переносимости — главное возражение к методу: модель обучается на
коленах 1–2 и проверяется на колене 3, которого не видела. AUC 0.64
out-of-depth против 0.73 in-sample; доля узлов без исходящих по коленам 1, 2, 3
держится в коридоре 0.65 / 0.58 / 0.64, то есть «терминальность» не дрейфует с
глубиной. Полный отчёт с коэффициентами и калибровкой — `out/censoring_report.json`.

Решение по ролям: обрезанный узел получает роль `terminal` только при
`terminal_p >= 0.70` (86 узлов), и его `role_score` равен этой вероятности.
Остальные 358 остаются `peripheral` с прямой формулировкой в `evidence`:
«обход обрезан 4-м коленом, вероятность что конечный 0.63 — роль не присваиваем».
Ожидаемое число настоящих конечных среди 444 — около 266, но какие именно,
по этим данным неизвестно, и инструмент это не скрывает.

В `graph.json` у каждого узла есть поля `terminal_status`
(`observed_sink` 1091 / `observed_forwarder` 694 / `unknown_truncated` 444 /
`no_edges` 19) и `terminal_p` — интерфейс показывает неопределённость явно.

## Ловушка 2: заниженный вход у seed

Граф собран ОТ seed по исходящим, поэтому деньги, полученные seed извне
выборки, в данных отсутствуют, и `pass_through` у них доходит до 22. Роль seed
определяется только по исходящему профилю (правило R3c), `pass_through` для них
не применяется, уверенность в роли ограничена 0.55, а в `evidence` прямо
написано: «входящие извне выборки не видны».

Тот же эффект есть и за пределами seed: 377 узлов графа отдают больше, чем по
данным получили, и 335 из них — не seed. Для них считается `unseen_inflow_kzt = max(out_kzt - in_kzt, 0)`
— объём, источник которого в выборке не виден, — и они получают роль `transit`
по правилу R3b, а не «периферия» с непонятным пропуском 2441%.

## Ловушка 3: суммы и количество переводов — разные сигналы

Считаются обе величины отдельно (`in_kzt`/`out_kzt` и `in_tx`/`out_tx`), плюс
средний размер перевода, максимальное ребро, концентрация входящих по сумме
(HHI) и максимум переводов от одного плательщика за один день (признак
дробления). В `evidence` всегда выводятся и сумма, и число переводов.

## Ловушка 4: направленность графа

Все ролевые метрики считаются на направленном графе: `in_deg`/`out_deg`,
`pagerank` по сумме, HITS (hub — источник рассылки, authority — сборщик),
`betweenness` на направленном графе. Неориентированная проекция используется
ровно в одном месте — кластеризация Louvain, потому что модульность определена
для неориентированных графов. Это оговаривается прямо: кластер отвечает на
вопрос «кто с кем связан деньгами», а направление внутри кластера
восстанавливается ролями узлов, посчитанными на направленном графе.

## Кластеры

Louvain (`seed=42`, вес `sum_kzt`) даёт 71 сообщество плюс кластер `-1` для 19
seed без рёбер. Нумерация по убыванию размера — стабильна между прогонами.
9 кластеров содержат 2+ seed. Гипотеза собирается из состава кластера
шаблоном: сколько seed, сколько точек сбора и веерных рассылок, есть ли
кандидаты над точками сбора, внутренний оборот, сколько уходит наружу, сколько
узлов обрезано обходом. Это формулировка «на что похоже и что проверять», а не
утверждение о виновности.

## Приоритет проверки

`priority_score` = взвешенная сумма шести компонент, каждая — перцентиль
наблюдаемой величины, итог нормируется на максимум по графу:

| Компонента | Вес | Что измеряет |
|---|---|---|
| `money` | 0.28 | перцентиль `max(in_kzt, out_kzt)` |
| `in_concentration` | 0.20 | перцентиль `in_deg` — сколько плательщиков сходится |
| `structure` | 0.16 | среднее перцентилей `betweenness` и `pagerank` |
| `seed_link` | 0.14 | прямая связь с известными следствию клиентами |
| `retention` | 0.10 | перцентиль осевшей суммы |
| `role` | 0.12 | вес роли в иерархии × уверенность в роли |

Отдельное решение: итоговый скор seed умножается на 0.5. Следствию эти 81
клиент уже известен, а инструмент нужен, чтобы показать невидимую часть сети
(ТЗ: «фокус проверки смещается с 81 курьера на реальные точки консолидации»).
Из выгрузок и со схемы seed при этом не исчезают.

В `top_nodes.csv` у каждой строки есть `why` — какие факты вытолкнули узел
наверх и в какие верхние проценты графа он попал по трём главным компонентам.

## Ограничения подхода

- Ground truth в данных нет; роли — гипотезы для проверки, а не квалификация
  деяния. Ни одна формулировка в выгрузках не утверждает виновность.
- Входящие потоки на узлы за пределами выборки не видны, поэтому полный баланс
  узла недоступен; `pass_through` у 377 узлов превышает 1 именно по этой причине.
- Транзакции ниже 5 000 KZT в выгрузку не попали: дробление ниже порога
  невидимо в принципе.
- Атрибутов клиента в данных нет и они не достраиваются.
- Для 444 узлов 4-го колена терминальность оценена вероятностью, а не
  установлена; ожидаемая ошибка модели видна в `out/censoring_report.json`.
- Louvain теряет направление рёбер на шаге кластеризации (см. ловушку 4).

## Масштабирование до ~1 млн узлов

Узкие места конвейера на текущем объёме — `betweenness_centrality` (O(V·E)) и
`simple_cycles`; они же первыми упрутся в стену. Замены: приближённый
betweenness по выборке источников (`k`-sample), поиск возвратных потоков только
на подграфе топ-узлов по обороту, Louvain на `igraph`/`graph-tool` вместо
networkx, хранение метрик в parquet и расчёт признаков в polars/DuckDB вместо
pandas. Правила ролей и пороги-квантили при этом не меняются: они формулируются
над распределениями и переносятся на любой объём без переобучения — что и
делает метод пригодным для потоковой работы банка, а не только для одной выгрузки.
