# Метод ядра анализа — «Граф денег»

## О чём этот документ

Как устроено ядро анализа: какие метрики считаются, по каким правилам
присваиваются роли, откуда взят каждый порог и чего метод не умеет. Общее
описание проекта и инструкция по запуску — в [README](../README.md); здесь
только метод.

**Задача.** Правоохранительные органы передали аналитику банка список 81
клиента, получавшего деньги от незаконного оборота. Из банковской выгрузки
собран граф: от этих 81 клиента прослежены исходящие переводы на четыре шага
вперёд — 2248 клиентов и 3119 связей между ними за июль 2026 года. Аналитику
нужно понять, кто в этой сети собирает деньги, кто прогоняет их дальше, у кого
они остаются, и **кого из 2248 проверять первым**.

**Что метод делает.** Каждому из 2248 клиентов присваивает роль в сети с
объяснением на числах, разбивает сеть на группы, ранжирует клиентов по
приоритету проверки и считает координаты для схемы. Размеченных «правильных»
ролей в данных нет, поэтому метод построен так, чтобы каждое решение можно было
проследить до конкретного правила и конкретного порога.

**Вход:** три файла `case/data/*.parquet` от организаторов кейса — клиенты,
связи, отдельные транзакции.

**Выход** (папка `out/`):

| Файл | Что внутри |
|---|---|
| `nodes_roles.csv` | строка на каждый из 2248 клиентов: роль, уверенность, кластер, приоритет, объяснение |
| `clusters.csv` | 72 группы: размер, состав, оборот, гипотеза о назначении |
| `top_nodes.csv` | 30 клиентов в порядке приоритета проверки с обоснованием |
| `graph.json` | всё то же одним файлом для интерфейса, включая координаты схемы |
| `thresholds.json` | значение и формулировка каждого порога |
| `censoring_report.json` | отчёт модели для узлов, обрезанных обходом |
| `robustness_report.json` | кривые устойчивости сети к изъятию узлов |

Запуск — одна команда из корня репозитория, без ручных шагов:

```bash
.venv/bin/python -m pipeline.run --data case/data --out out
```

Около 14 секунд на предоставленном объёме при лимите ТЗ в 300 секунд. Прогон
воспроизводим побайтово: два запуска подряд дают идентичные CSV и `graph.json`,
отличающийся только полями `meta.generated_at` и `meta.pipeline_seconds`.
Случайность в методе есть только в двух местах, и оба зафиксированы
константой `seed=42`: кластеризация и случайная базовая линия в оценке
устойчивости.

## Словарь терминов

Термины из выгрузки и из этого документа. Названия полей совпадают с колонками
`nodes_roles.csv`.

| Термин | Что означает |
|---|---|
| `gid` | обезличенный идентификатор клиента; ни имён, ни ИИН в данных нет |
| seed | один из 81 клиента, известного следствию, — точка входа обхода |
| колено, `depth` | сколько шагов по переводам от ближайшего seed: 0 — сам seed, 4 — край выгрузки |
| `in_deg` / `out_deg` | от скольких разных клиентов узел получил / скольким отправил |
| `in_kzt` / `out_kzt` | сколько получил / отправил тенге в пределах выгрузки |
| `in_tx` / `out_tx` | количество отдельных переводов |
| `pass_through` | `out_kzt / in_kzt` — какая доля полученного ушла дальше |
| `retained_kzt` | сколько денег осталось на узле: `in_kzt − out_kzt`, но не меньше нуля |
| `unseen_inflow_kzt` | на сколько узел отдал больше, чем получил по данным, — приток извне выгрузки |
| `pagerank` | влиятельность узла в потоке денег, с учётом сумм переводов |
| `betweenness` | посредничество: через сколько кратчайших денежных цепочек проходит узел |
| HITS: `hub` / `authority` | склонность рассылать / склонность собирать |
| HHI | концентрация: 1.0 — весь приток от одного плательщика, ближе к 0 — от многих равномерно |
| Louvain | алгоритм разбиения сети на группы плотно связанных узлов |
| квантиль 0.975 | значение, которое превышают 2.5% узлов графа |
| AUC | качество модели: 1.0 — идеальное разделение, 0.5 — угадывание монеткой |

## Конвейер

```
parquet (edges, nodes, transactions)
  → проверки консистентности (edges == transactions, gid уникален)
  → направленный взвешенный граф (DiGraph, вес = sum_kzt)
  → метрики узла: структура, деньги, время
  → модель обрыва обхода → terminal_status, terminal_p
  → временные паттерны → флаги транзита, синхронного сбора, дробления
  → роли по формальным правилам (пороги = квантили)
  → coordinator: второй проход по иерархии плательщиков
  → кластеры (Louvain на неориентированной проекции) + гипотезы
  → priority_score (7 взвешенных компонент) + топ-30 с обоснованием
  → устойчивость: изъятие топ-N против случайного
  → четыре файла в out/ + три отчёта метода
```

## Пороги (считаются на прогоне)

Пороги не подобраны руками под желаемый ответ: почти все они — квантили
распределений самих данных, посчитанные на прогоне, и потому переносятся на
другую выгрузку без переобучения. Исключения названы в таблице прямо: два
порога смысловые — «не более двух суток» взято из формулировки ТЗ, а
`terminal_p_min` — наше решение о том, при какой вероятности мы готовы назвать
узел конечным получателем. Машинно-читаемая копия таблицы, включая формулировку
каждого порога, — в `out/thresholds.json`.

| Порог | Правило | Значение на этих данных |
|---|---|---|
| `in_deg_consolidator` | квантиль 0.975 распределения `in_deg` | 4 плательщика |
| `out_deg_distributor` | квантиль 0.975 распределения `out_deg` | 11 получателей |
| `materiality_kzt` | медиана `in_kzt` среди узлов с поступлениями | 50 000 KZT |
| `in_money_high_kzt` | квантиль 0.95 распределения `in_kzt` | 613 779 KZT |
| `betweenness_high` | квантиль 0.99 `betweenness` | верхний 1% |
| `retention_pass_through` | квантиль 0.20 `pass_through` среди передающих дальше | 0.26 |
| `transit_pass_through` | коридор ±20% вокруг единицы | 0.8 … 1.2 |
| `terminal_p_min` | смысловое решение (см. ниже) | 0.70 |
| `sync_same_day_payers` | квантиль 0.95 (узлы с 2+ плательщиками) | 3 плательщика в день |
| `structuring_same_day_tx` | квантиль 0.99 переводов от одного плательщика за день | 3 перевода |
| `structuring_in_tx` | квантиль 0.95 `in_tx` при среднем платеже ниже квантиля 0.25 | 7 поступлений / 16 508 KZT |
| `fast_transit_days` | формулировка ТЗ, п. 8 | 2 суток |

### Как читать эту таблицу

Возьмём главный порог — «много плательщиков», от которого зависит роль
`consolidator`. В этом графе половина клиентов получает переводы ровно от
одного плательщика, 90% — не более чем от двух, и только 2.5% — от четырёх и
более; максимум — 24 плательщика. Квантиль 0.975 даёт 4, и это 89 клиентов из
2248. Порог не выбран руками: он означает «узел в верхних 2.5% графа по числу
плательщиков». Взяли бы 3 — в выборку попало бы 200 узлов, включая обычные
бытовые счета; взяли бы 8 — остались бы 17 самых ярких и потерялись бы точки
сбора среднего звена.

Так же устроен порог веерной рассылки: медиана `out_deg` равна нулю (больше
половины клиентов ничего не отправляют), квантиль 0.975 — 11 получателей, это
58 клиентов, а максимум в графе — 116 получателей.

Смысл квантилей вместо круглых чисел: при другой выгрузке — другой банк, другой
период, другой масштаб сумм — пороги пересчитаются сами и сохранят смысл
«верхние 2.5% сети», тогда как зашитая четвёрка на графе другой плотности
означала бы совсем другое.

Ядро системы — три зоны по доле пропуска `pass_through = out_kzt / in_kzt`:
прошло почти всё (транзит), почти всё осело (конечный получатель), между
(смешанный профиль — роль не утверждаем). Число плательщиков и получателей
отделяет сбор от веерной рассылки.

## Роли и правила их присвоения

Словарь ролей задан в ТЗ кейса, мы его не расширяли:

| Роль | Что означает для аналитика |
|---|---|
| `consolidator` | точка консолидации: деньги сходятся от нескольких участников |
| `transit` | транзит: деньги проходят дальше, не задерживаясь |
| `distributor` | веерное распределение на много получателей |
| `terminal` | конечный получатель: деньги пришли и остались |
| `coordinator` | узел над точками сбора, кандидат в распорядители средств |
| `peripheral` | признаков роли не выявлено |

Правила применяются в фиксированном порядке, первое сработавшее побеждает.
Порядок — часть метода: сначала проверяются самые выраженные формы поведения
(веер, сходимость), потом более слабые. `rule_id` каждого узла записан в
`nodes_roles.csv` и в `graph.json` — по любому gid видно, каким именно правилом
присвоена роль и, значит, что именно нужно перепроверить, если аналитик не
согласен.

| Правило | Условие | Узлов |
|---|---|---|
| R0 `peripheral` | нет ни одного ребра в выгрузке | 19 |
| R1 `distributor` | `out_deg >= 11` | 54 |
| R2 `consolidator` | `in_deg >= 4` и (`out_deg <= max(2, in_deg/2)` или `pass_through <= 0.5`) | 43 |
| R3a `transit` | `0.8 <= pass_through <= 1.2` | 67 |
| R3b `transit` | `pass_through > 1.2` — отдал больше, чем получил по данным | 249 |
| R3c `transit` | seed с исходящими: роль по исходящему профилю | 40 |
| R3d `transit` | ≥60% исходящей суммы ушло в пределах 2 суток после поступления и `pass_through >= 0.6` | 25 |
| R4a `terminal` | исходящих нет, и они проверены обходом (`depth <= 3`) | 1069 |
| R4b `terminal` | исходящие есть, но дальше уходит ≤26% — сумма осела | 105 |
| R4c `terminal` | обрезан 4-м коленом, `terminal_p >= 0.70` | 86 |
| R5 `peripheral` | смешанный профиль ниже всех порогов | 464 |
| R6 `coordinator` | иерархия + деньги (второй проход, см. ниже) | 27 |

`coordinator` — три условия одновременно: (1) узел получает минимум от двух
плательщиков, которые сами собирают деньги от 4+ плательщиков, либо напрямую
минимум от двух seed; (2) поступления в верхних 5% распределения `in_kzt`;
(3) узел не seed — 81 нижнее звено следствию уже известно, и входящие суммы у
них занижены по устройству выгрузки. Правило намеренно узкое: 27 кандидатов из
2248 — это список на проверку, а не вывод о роли в группе.

### Почему больше половины сети — конечные получатели

Роль `terminal` у 1260 узлов (56% графа), и это не результат наивного
`out_deg == 0`. Она складывается из трёх разных оснований, и в выгрузке они
различаются по `rule_id`, а в `graph.json` — в блоке `meta.terminal_breakdown`:

| Основание | Узлов | Что это значит |
|---|---|---|
| R4a | 1069 | исходящих переводов нет, и обход их запрашивал — отсутствие проверено |
| R4b | 105 | исходящие есть, но дальше ушло ≤26% — сумма фактически осела |
| R4c | 86 | обход обрезан 4-м коленом, вероятность конечного ≥0.70 |

Причина самой величины — устройство выгрузки: граф собран по ИСХОДЯЩИМ
переводам от 81 seed на четыре колена, поэтому нижний слой выборки по
построению состоит из получателей. Из 1260 узлов материальны (поступления не
ниже медианы графа) 623, остальные 637 получили меньше 50 000 KZT и отмечены
в `evidence` как мелкие получатели с `role_score` 0.65 вместо 0.9. Всего в
конечных получателях осело 164.9 млн KZT из 365.9 млн оборота.

`role_score` — уверенность в роли, а не важность узла: насколько узел ушёл за
порог своего правила (для `terminal` по обрезанным узлам — ровно вероятность по
модели, без округления вверх; для seed ограничена 0.55, потому что их приток не
наблюдаем).

## Четыре особенности данных, на которых ломаются наивные решения

Организаторы кейса заранее объявили четыре свойства выгрузки и прямо указали,
что их учёт оценивается (`case/starter/README.md`, раздел «Четыре ловушки»).
Ниже — что каждое из них означает и как оно закрыто в методе. Первые две —
главные: они меняют не отдельную метрику, а сами правила присвоения ролей.

### Особенность 1: обрыв обхода на 4-м колене

444 узла имеют `depth = 4` и `out_deg = 0`. Наивное правило
«`out_deg == 0` ⇒ конечный получатель» дало бы 444 ложных вывода.

Что наблюдаемо:

| Узел | Исходящие запрашивались обходом? | Вывод |
|---|---|---|
| `depth <= 3`, `out_deg = 0` | да, и их не нашлось | конечный получатель подтверждён данными |
| `depth <= 3`, `out_deg >= 1` | да | передаёт дальше |
| `depth = 4`, `out_deg = 0` | нет, обход остановлен | неизвестно, нужна оценка |

Метод: на коленах 1–3 факт «есть ли исходящие» наблюдаем, поэтому там можно
измерить связь этого факта с ВХОДЯЩИМ профилем узла и профилем его
плательщиков — а и то, и другое у 4-го колена видно полностью (его плательщики
лежат на 3-м колене и измерены). Логистическая регрессия на 10 интерпретируемых
признаках обучается на 1723 узлах колен 1–3 и применяется к 444 обрезанным,
давая `terminal_p`.

Признаки: сумма и число поступлений, число плательщиков, средний размер
поступления, концентрация входящих, сколько дней до конца периода оставалось
после последнего поступления, широта рассылки плательщиков (макс. и средняя),
доля денег от веерных плательщиков, число плательщиков-seed.

Проверка переносимости — главное возражение к методу: модель обучается на
коленах 1–2 и проверяется на колене 3, которого не видела. AUC 0.64
out-of-depth против 0.73 in-sample; доля узлов без исходящих по коленам 1, 2, 3
держится в коридоре 0.65 / 0.58 / 0.64, то есть «терминальность» не дрейфует с
глубиной. Полный отчёт с коэффициентами и калибровкой — `out/censoring_report.json`.

**Можно ли читать `terminal_p` как вероятность.** Да, модель калиброванна —
это видно по обучающей выборке: среди узлов с предсказанием около 0.72
конечными оказались 71.1%, около 0.82 — 82.4%, около 0.13 — 11.4%. Полная
таблица калибровки в `out/censoring_report.json`.

**Почему порог именно 0.70.** Разброс `terminal_p` у 444 обрезанных узлов узкий
— от 0.14 до 0.80 при медиане 0.60. Причина видна в данных: 98% этих узлов
получили переводы всего от одного плательщика, то есть входной профиль у них
почти одинаковый и различать их можно лишь по сумме, дробности и профилю
плательщика. Что дают разные пороги:

| Порог | Получат роль `terminal` | Ожидаемо верных | Ожидаемо ошибочных |
|---|---|---|---|
| 0.50 | 383 узла (86% обрезанных) | ~243 | ~140 |
| 0.60 | 236 узлов (53%) | ~160 | ~76 |
| 0.65 | 121 узел (27%) | ~88 | ~33 |
| **0.70** | **86 узлов (19%)** | **~65** | **~21** |
| 0.75 | 44 узла (10%) | ~34 | ~10 |

Мы выбрали 0.70 потому, что ошибка здесь несимметрична. Ложно названный
конечный получатель закрывает аналитику направление поиска: он решит, что
деньги остановились, и не запросит дальнейшую выгрузку. Пропущенный конечный
получатель ничего не закрывает — узел просто остаётся с ролью `peripheral`
и пометкой, что обход обрезан. Поэтому порог смещён в сторону осторожности:
из 444 узлов роль получают 86, при ожидаемых 21 ошибке вместо 140 при пороге
0.50.

Порог задан одной константой `TERMINAL_P_MIN` в `config.py`, а само значение
`terminal_p` выгружается для каждого узла — если аналитик считает нашу
осторожность чрезмерной, он отбирает узлы по своему порогу прямо в выгрузке.

Решение по ролям: обрезанный узел получает роль `terminal` только при
`terminal_p >= 0.70` (86 узлов), и его `role_score` равен этой вероятности.
Остальные 358 остаются `peripheral` с прямой формулировкой в `evidence`:
«обход обрезан 4-м коленом, вероятность что конечный 0.63 — роль не присваиваем».
Ожидаемое число настоящих конечных среди 444 — около 266, но какие именно,
по этим данным неизвестно, и инструмент это не скрывает.

В `graph.json` у каждого узла есть поля `terminal_status`
(`observed_sink` 1091 / `observed_forwarder` 694 / `unknown_truncated` 444 /
`no_edges` 19) и `terminal_p` — интерфейс показывает неопределённость явно.

### Особенность 2: заниженный вход у seed

Граф собран ОТ seed по исходящим, поэтому деньги, полученные seed извне
выборки, в данных отсутствуют, и `pass_through` у них доходит до 22. Роль seed
определяется только по исходящему профилю (правило R3c), `pass_through` для них
не применяется, уверенность в роли ограничена 0.55, а в `evidence` прямо
написано: «входящие извне выборки не видны».

Тот же эффект есть и за пределами seed: 377 узлов графа отдают больше, чем по
данным получили, и 335 из них — не seed. Для них считается
`unseen_inflow_kzt = max(out_kzt - in_kzt, 0)` — объём, источник которого в
выборке не виден. Такой узел получает роль `transit` по правилу R3b: он ничего
не удерживает, а не «периферию» с необъяснимым пропуском в 2441%.

### Особенность 3: суммы и количество переводов — разные сигналы

Считаются обе величины отдельно (`in_kzt`/`out_kzt` и `in_tx`/`out_tx`), плюс
средний размер перевода, максимальное ребро, концентрация входящих по сумме
(HHI) и максимум переводов от одного плательщика за один день (признак
дробления). В `evidence` всегда выводятся и сумма, и число переводов.

### Особенность 4: направленность графа

Все ролевые метрики считаются на направленном графе: `in_deg`/`out_deg`,
`pagerank` по сумме, HITS (hub — источник рассылки, authority — сборщик),
`betweenness` на направленном графе. Неориентированная проекция используется
ровно в одном месте — кластеризация Louvain, потому что модульность определена
для неориентированных графов. Это оговаривается прямо: кластер отвечает на
вопрос «кто с кем связан деньгами», а направление внутри кластера
восстанавливается ролями узлов, посчитанными на направленном графе.

## Временные паттерны: когда деньги пришли и когда ушли

Дополнительная часть кейса (ТЗ, п. 8). Структура графа не отличает узел, у которого деньги лежали две недели, от
узла, отдавшего их в тот же день. Три признака считаются по
`transactions.parquet`, входят в `evidence`, в компоненту `timing` приоритета и
выгружаются отдельными полями — новых ролей они не создают.

| Признак | Правило | Узлов |
|---|---|---|
| `flag_fast_transit` | медиана удержания ≤2 суток И ≥60% исходящей суммы ушло в этом окне | 233 |
| `flag_sync_collection` | в один день заплатили ≥3 разных плательщиков (квантиль 0.95) | 38 |
| `flag_structuring` | ≥3 перевода от одного плательщика за день (квантиль 0.99), либо ≥7 поступлений при среднем платеже ≤16.5 тыс. | 74 |
| любой из трёх | — | 287 |

Возвратные потоки (ТЗ, п. 8) считаются по структуре графа и выгружаются
колонками, в роли и приоритет не входят: `mutual_pair` — узел участвует во
взаимной паре переводов A→B и B→A (266 узлов), `in_cycle` — узел лежит на
направленном цикле длиной до 6 (303 узла). Это признак для проверки: деньги
вернулись к отправителю через посредников.

Для быстрого транзита одной медианы недостаточно: узел может быстро отдать
мелочь и придержать основную сумму, поэтому второе условие — про долю суммы,
а не про число переводов. Дробление ловится в двух видах: собранное в один день
и растянутое по дням.

В топ-30 приоритетов 13 узлов с синхронным сбором, 16 со сквозным транзитом и
9 с признаками дробления — то есть временные признаки не лежат отдельной
витриной, а влияют на порядок проверки.

## Кластеры

Louvain (`seed=42`, вес `sum_kzt`) даёт 71 сообщество плюс кластер `-1` для 19
seed без рёбер. Нумерация по убыванию размера — стабильна между прогонами.
9 кластеров содержат 2+ seed. Гипотеза собирается из состава кластера
шаблоном: сколько seed, сколько точек сбора и веерных рассылок, есть ли
кандидаты над точками сбора, внутренний оборот, сколько уходит наружу, сколько
узлов обрезано обходом. Это формулировка «на что похоже и что проверять», а не
утверждение о виновности.

## Приоритет проверки

`priority_score` = взвешенная сумма семи компонент, каждая — перцентиль
наблюдаемой величины, итог нормируется на максимум по графу:

| Компонента | Вес | Что измеряет |
|---|---|---|
| `money` | 0.25 | перцентиль `max(in_kzt, out_kzt)` |
| `in_concentration` | 0.18 | перцентиль `in_deg` — сколько плательщиков сходится |
| `structure` | 0.14 | среднее перцентилей `betweenness` и `pagerank` |
| `seed_link` | 0.12 | прямая связь с известными следствию клиентами |
| `retention` | 0.09 | перцентиль осевшей суммы |
| `role` | 0.12 | вес роли в иерархии × уверенность в роли |
| `timing` | 0.10 | сильнейший из временных признаков (см. выше) |

Отдельное решение: итоговый скор seed умножается на 0.5. Следствию эти 81
клиент уже известен, а инструмент нужен, чтобы показать невидимую часть сети
(ТЗ: «фокус проверки смещается с 81 курьера на реальные точки консолидации»).
Из выгрузок и со схемы seed при этом не исчезают.

В `top_nodes.csv` у каждой строки есть `why` — какие факты вытолкнули узел
наверх и в какие верхние проценты графа он попал по трём главным компонентам.

## Раскладка схемы: координаты считает ядро, а не браузер

Силовая симуляция на клиенте давала «комки одинаковых шариков»: она
минимизирует длину рёбер, а не показывает смысл кейса, считается медленно на
телефоне и даёт разную картинку от запуска к запуску. Координаты считаются в
пайплайне и лежат в `nodes[].x`, `nodes[].y` — нормированы в [0, 1], единый
масштаб по осям, `y` растёт вверх. Интерфейс только рисует.

Метод — радиальные клинья:

    радиус = колено обхода: seed в центре, 4-е колено по краю
    угол   = кластер: непрерывный клин, ширина ∝ числу узлов
    внутри клина = по priority_score, важные ближе к оси клина

Почему клин, а не концентрические кольца с секторами внутри каждого: при
секторах внутри кольца кластер разрезается на четыре отдельные дуги и
перестаёт читаться как целое. Клин даёт обе оси смысла сразу — движение денег
от seed наружу читается радиально, границы кластеров угловые, а точка
консолидации опознаётся как узел, в который входят стрелки из соседних
клиньев. Проверяется по данным: средний радиус узла в главной панели растёт
монотонно с коленом — 0.060, 0.119, 0.175, 0.232, 0.290.

Порядок клиньев по кругу подобран жадно по силе межкластерных денежных связей:
связанные кластеры стоят рядом, поэтому хорды между ними короткие и не режут
схему через центр.

Компоненты не смешиваются — 17 панелей:

| Панель | Содержимое | Радиус |
|---|---|---|
| главная | крупнейшая компонента, 1877 узлов, 56 клиньев | 0.291 |
| островок 1 | вторая компонента, 270 узлов | 0.110 |
| островки 2–15 | компоненты от 2 до 17 узлов, полосой справа | 0.017…0.028 |
| без рёбер | 19 seed, решёткой — кольца и клинья им нечего показывать | 0.038 |

Площадь делится не поровну: радиус островка ∝ √(числа узлов), то есть площадь
пропорциональна размеру компоненты, и главная панель остаётся доминирующей.

Наложения разведены: внутри пары (клин, колено) шаг по дуге не меньше
минимального, при нехватке места группа разбивается на подслои по радиусу
внутри полосы своего кольца (полоса — 85% расстояния до следующего кольца:
меньше — узлы теснятся на самой окружности, больше — кольца сливаются).
Остаток разводится расталкиванием без притяжения, со смещением не более 0.02
от места в клине, порядок пар фиксирован — случайности нет. Результат
проверяется KD-деревом и пишется в `meta.layout`: минимальный зазор 0.0060,
медианный 0.0085, узлов ближе 0.005 — ноль.

Для подложки сектора в `clusters[]` лежат `center_x`, `center_y`, `radius`
(по факту координат) и угловая геометрия клина `angle_start`, `angle_end`,
`r_inner`, `r_outer` плюс номер панели `panel`; центры и радиусы самих панелей —
в `meta.layout.панели`. У кластера `-1` (seed без рёбер) угловой геометрии нет,
поля заполнены `null`.

Координаты идентичны между прогонами — проверено сравнением двух запусков.

## Устойчивость сети: проверка, что ранжирование работает

Пересчёт компонент и отрезанного оборота при изъятии топ-N делает интерфейс на
загруженных данных. Пайплайн считает то, чего в браузере дёшево не получить, —
СЛУЧАЙНУЮ БАЗОВУЮ ЛИНИЮ: изъятие N случайных узлов, 20 повторов на каждое
значение N от 0 до 50, `seed=42`. Без неё фраза «изъятие 20 узлов рвёт сеть»
непроверяема: может, её порвут любые 20 узлов.

Результат (`meta.robustness`, полные кривые — в `out/robustness_report.json`).
Как читать столбцы: «отрезано оборота» — доля тенге на связях, задетых изъятием
(больше — лучше для следствия); «оборот на маршрутах от seed» — сколько
процентов оборота ещё достижимо от оставшихся seed по направлению переводов
(меньше — лучше); «крупнейшая компонента» — какая доля оставшихся узлов всё
ещё связана в один кусок (меньше — сеть сильнее раздроблена).

| Изъято | Отрезано оборота: топ-N / случайные N | Оборот на маршрутах от seed: топ-N / случайные N | Крупнейшая компонента: топ-N / случайные N |
|---|---|---|---|
| 10 | 5.0% / 1.2% (×4.3) | 94.8% / 98.4% | 0.82 / 0.83 |
| 20 | 9.4% / 1.7% (×5.7) | 90.1% / 97.9% | 0.80 / 0.83 |
| 30 | 15.4% / 3.4% (×4.5) | 83.5% / 95.7% | 0.77 / 0.82 |
| 50 | 22.3% / 4.3% (×5.2) | 73.3% / 94.8% | 0.75 / 0.81 |

Что мы говорим жюри прямо: размер крупнейшей компоненты расходится слабо —
20 узлов из 2248 в разреженном графе связность не рвут (0.80 против 0.83), и
выдавать это за развал сети мы не будем; заметным разрыв становится только к
50 изъятым (0.75 против 0.81). Главное расхождение в другом: изъятие топ-20 по нашему
приоритету отрезает 9.4% оборота против 1.7% при случайном выборе — в 5.7 раза
больше, а доля оборота, остающегося на маршрутах от известных следствию
клиентов, падает до 90.1% против 97.9%. Это и есть проверяемое доказательство,
что `priority_score` выбирает узлы, на которых держатся денежные потоки, а не
просто крупные счета.

Метрика достижимости считается направленным обходом от живых seed по исходящим
рёбрам: именно она отвечает на вопрос следствия «сколько денежных маршрутов от
известных клиентов перестанет работать».

## Поведение на неожиданных данных

Пайплайн проверен на девяти вырожденных наборах. Принцип разделения: если
странность делает результат неверным — прогон останавливается с кодом 2 и
сообщением на русском; если странность поддаётся расчёту — прогон идёт дальше,
но печатает предупреждение, чтобы решение принимал аналитик, а не пайплайн.

| Что подсунули | Поведение |
|---|---|
| узел без единого ребра | считается штатно: в выгрузке организаторов таких 19, все seed, роль `peripheral` |
| отрицательная сумма перевода | предупреждение: доля пропуска и осевшие суммы у этих узлов посчитаются, но смысла не имеют |
| дубль пары плательщик→получатель | остановка: при сборке графа второе ребро молча затрёт первое и часть оборота исчезнет из расчёта |
| перевод клиента самому себе | предупреждение: петля учтена и во входящих, и в исходящих, доля пропуска завышена |
| пустой `edges.parquet` | предупреждение «рёбер нет вовсе», все узлы получают `peripheral`, выгрузки создаются |
| пустой `nodes.parquet` | остановка: считать нечего |
| граф из одного узла | считается штатно |
| ни одного seed | предупреждение: приоритет считается без компоненты связи с известными клиентами |
| `edges` и `transactions` не сходятся | остановка: названо, сколько пар расходится по сумме и по числу переводов |
| папки с данными нет, файл отсутствует | остановка: названо, какого файла не хватает |

Допуск при сверке сумм — одна копейка: на выгрузке организаторов расхождение
между ребром и суммой его транзакций не превышает 6·10⁻¹¹, то есть ошибку
округления `float` мы отличаем от битых данных.

Найденное при этой проверке и исправленное: оценка устойчивости изымала до 50
узлов независимо от размера графа и падала на любом наборе меньше 50 узлов;
HITS падал внутри `scipy` на графе без рёбер; при полном отсутствии транзакций
не создавались временные колонки; в `meta` мог попасть `NaN` (например, AUC не
определён, если в выборке остался один класс), а `JSON.parse` в браузере на
`NaN` падает — теперь документ рекурсивно очищается на выходе. На выгрузке
организаторов ни одно из этих исправлений результат не меняет: выгрузки до и
после совпадают поле в поле.

## Ограничения подхода

- Ground truth в данных нет; роли — гипотезы для проверки, а не квалификация
  деяния. Ни одна формулировка в выгрузках не утверждает виновность.
- Входящие потоки на узлы за пределами выборки не видны, поэтому полный баланс
  узла недоступен; `pass_through` у 354 узлов превышает 1 именно по этой причине.
- Транзакции ниже 5 000 KZT в выгрузку не попали: дробление ниже порога
  невидимо в принципе.
- Атрибутов клиента в данных нет и они не достраиваются.
- Для 444 узлов 4-го колена терминальность оценена вероятностью, а не
  установлена; ожидаемая ошибка модели видна в `out/censoring_report.json`.
- Louvain теряет направление рёбер на шаге кластеризации (см. особенность 4).

## Масштабирование до ~1 млн узлов

Реализация не проверялась на таком объёме, поэтому ниже — не обещание, а разбор
по замеренному профилю. Из 14 секунд прогона на 2248 узлах время расходуется так:

| Этап | Время | Доля |
|---|---|---|
| метрики узла (`features.py`) | 7.9 с | 57% |
| устойчивость: 1071 пересчёт связности (`robustness.py`) | 4.1 с | 30% |
| роли и тексты обоснований | 0.6 с | 4% |
| приоритет | 0.5 с | 4% |
| раскладка | 0.5 с | 3% |
| кластеризация, загрузка, модель обрыва, паттерны | < 0.3 с | 2% |

Внутри метрик узла самая дорогая часть — `betweenness_centrality`, 2.2 секунды:
она растёт как O(V·E) и на миллионе узлов станет неприемлемой первой. Замена —
приближённый betweenness по выборке источников (`k`-sample), это штатный режим
networkx. Остальное время метрик уходит на признаки, считаемые построчно
(временные паттерны, концентрация входящих), — они переносятся на групповые
операции в polars или DuckDB без изменения смысла.

Оценка устойчивости масштабируется иначе: её стоимость задаём мы сами — 51
значение N и 20 случайных повторов. На большом графе достаточно считать её на
подграфе топ-узлов по обороту и реже по сетке N, либо ограничить кривую теми
значениями, которые нужны интерфейсу.

Поиск коротких циклов (`simple_cycles` с ограничением длины 6) на текущем
объёме дешёв — 0.1 секунды, — но его стоимость растёт экспоненциально с
плотностью, поэтому на миллионе узлов его нужно ограничивать подграфом, а не
запускать на всей сети.

Louvain на `igraph` вместо networkx даст порядок по скорости. Хранение метрик —
parquet вместо CSV.

Главное, что при росте объёма не меняется: правила ролей и пороги. Они
сформулированы над квантилями распределений, поэтому переносятся на любой
объём без переобучения, а модель для обрезанных узлов переобучается на самих
данных за один проход. Это и делает метод пригодным для регулярной работы
банка, а не только для одной разовой выгрузки.
