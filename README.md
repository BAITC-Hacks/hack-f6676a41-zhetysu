# Граф денег

Восстановление финансовой структуры организованной группы по транзакционной сети.

**Развёрнутая версия: https://zhetysu-team.kz**

Команда Zhetysu · HackAlem AI, 23 сентября 2026 · кейс «Граф денег»

---

## Что решает и для кого

Пользователь — AML-аналитик подразделения финансового мониторинга банка второго уровня.

По итогам оперативной информации ему известен только нижний уровень цепочки: 81 клиент,
получавший деньги, связанные с незаконным оборотом. Кто собирает эти средства, через кого
их прогоняют и у кого они оседают, приходится восстанавливать вручную — часы работы на один
узел, четыре колена, без ранжирования. В результате блокируется периферия, а организаторы
сохраняют инфраструктуру.

Инструмент отвечает на один вопрос: **кого из 2248 клиентов смотреть первым и почему**.
Аналитик получает ранжированный список с обоснованием по каждому узлу вместо ручной
трассировки.

## Что реализовано

- **Воспроизводимый пайплайн** — один запуск от сырых `.parquet` до трёх выгрузок,
  без ручных шагов. На предоставленном объёме отрабатывает за 10 секунд.
- **Роль и обоснование у каждого из 2248 узлов** — роль из словаря ТЗ, уверенность,
  номер кластера, приоритет проверки и `evidence`: человекочитаемое объяснение с числами.
- **Документированные критерии ролей** — 12 правил с порогами, у каждого узла записан
  `rule_id`. По любому gid видно, каким правилом присвоена роль.
- **Пороги считаются на прогоне** — из квантилей распределений самих данных, а не заданы
  вручную. Значения и формулировка каждого порога выгружаются в `out/thresholds.json`.
- **Кластеризация** — 72 сообщества, по каждому размер, число seed, внутренний оборот,
  состав по ролям и гипотеза о назначении.
- **Топ-лист приоритетов** — 30 узлов с обоснованием, почему узел в этой позиции.
- **Веб-интерфейс** — схема сети с направлением потоков, поиск по gid, досье узла,
  топ-лист, кластеры, светлая и тёмная темы, адаптив под телефон.
- **Отделение настоящих конечных получателей от обрезанных обходом** — см. ниже,
  это основное методическое решение проекта.
- **Симулятор изъятия узлов** — пересчёт связности сети при удалении топ-N. Изъятие
  20 узлов по нашему приоритету отрезает 9,4% оборота, изъятие 20 случайных — 1,7%:
  ранжирование проверяется само собой, а не декларируется.
- **Поиск по графу вопросом словами** — «кого смотреть первым», «кто собирает деньги
  с этих двоих», «куда уходят деньги от такого-то». Ответ считается по данным
  детерминированно; языковая модель, если ключ задан, только переформулирует готовый
  текст и не может изменить ни одной цифры.
- **Раскладка схемы считается в пайплайне** — радиальные клинья: seed в центре, колена
  обхода кольцами наружу, кластеры секторами, внутри сектора важные узлы ближе к оси.
  Картинка одинакова при каждом прогоне, браузер только рисует готовые координаты.

## Как работает основной сценарий

1. Аналитик открывает интерфейс и видит схему сети: направление потоков, цвет по роли,
   группировка по кластерам.
2. Вводит gid — узел подсвечивается, открывается досье: роль с обоснованием, сколько
   получил и отдал, от скольких и скольким, доля пропуска, колено, кластер, связи.
3. Открывает топ-лист приоритетов и читает обоснование по каждому узлу, например:
   «получает от 11 разных плательщиков, отдаёт дальше 3% полученного».
4. Двигает ползунок «изъять топ-N» и видит, на сколько фрагментов распалась сеть
   и какая доля оборота отрезана.
5. Формирует перечень клиентов на углублённую проверку.

## Методическое ядро: почему «нет исходящих» не значит «деньги осели»

Граф собран обходом от 81 seed-клиента по исходящим переводам на глубину 4 колена.
444 узла лежат на последнем колене и не имеют исходящих переводов — **но это артефакт
сбора данных, а не поведение денег**: обход закончился на них. Наивное правило
`out_deg == 0 ⇒ конечный получатель` дало бы 444 ложных вывода.

Решение: узлы разделены по наблюдаемости, поле `terminal_status`.

| Статус | Узлов | Смысл |
|---|---|---|
| `observed_sink` | 1091 | деньги пришли и остались; исходящие проверены обходом |
| `observed_forwarder` | 694 | деньги пришли и ушли дальше |
| `unknown_truncated` | 444 | узел на 4-м колене, исходящие никто не выгружал |
| `no_edges` | 19 | seed без единого ребра в выгрузке |

Для 444 обрезанных узлов роль не назначается по факту отсутствия рёбер. Вместо этого
считается `terminal_p` — вероятность того, что узел действительно конечный получатель.
Модель (логистическая регрессия на 10 признаках входящего профиля узла и профиля его
плательщиков, которые у 4-го колена наблюдаемы полностью) обучена на коленах 1–3.

Проверка переносимости: обучение на коленах 1–2, проверка на невиданном колене 3 —
AUC 0.64 против 0.73 in-sample. Модель переносится хуже, чем на своей выборке, поэтому
порог поставлен высоко: роль `terminal` получают только 86 узлов с `terminal_p >= 0.70`.
Остальные 358 остаются `peripheral` с честной формулировкой в `evidence`.

Аналогично закрыта вторая ловушка данных: у seed-клиентов входящие суммы занижены по
устройству выгрузки, поэтому их роль считается только по исходящему профилю,
`pass_through` к ним не применяется, а уверенность ограничена 0.55.

Полное описание метода, все пороги и ограничения подхода — в [`pipeline/METHOD.md`](pipeline/METHOD.md).

| Слой | Выбор |
|---|---|

## Архитектура

```
case/data/*.parquet          исходные данные организаторов (только чтение)
        │
        ▼
pipeline/                    ядро анализа
  data.py                    загрузка и проверки консистентности
  graphbuild.py              направленный взвешенный граф
  features.py                25 признаков узла: степени, обороты, пропуск, посредничество
  censoring.py               модель terminal_p для узлов, обрезанных обходом
  roles.py                   12 правил с порогами, rule_id у каждого узла
  clusters.py                сообщества и гипотезы по ним
  priority.py                приоритет проверки
  export.py                  выгрузки
  run.py                     единая точка входа
        │
        ▼
out/                         результат
  nodes_roles.csv            2248 строк, схема ТЗ
  clusters.csv               72 кластера
  top_nodes.csv              30 узлов
  graph.json                 всё то же для интерфейса, одним файлом
  thresholds.json            значение и обоснование каждого порога
  censoring_report.json      отчёт модели terminal_p
        │
        ▼
server.py  ──>  web/         интерфейс читает out/graph.json
   │
   └─ ask.py                 вопрос словами: разбор, поиск по графу, необязательная
                             переформулировка моделью
```

Ядро и интерфейс связаны **только** через `out/graph.json`. Контракт зафиксирован
в [`docs/spec.md`](docs/spec.md).

## Установка

Нужен Python 3.10 или новее. Больше ничего.

```bash
git clone https://github.com/BAITC-Hacks/hack-f6676a41-zhetysu.git
cd hack-f6676a41-zhetysu
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

## Запуск

```bash
.venv/bin/python -m pipeline.run --data case/data --out out
.venv/bin/python server.py --port 3300
```

Первая команда считает роли и пишет выгрузки в `out/`. Вторая поднимает интерфейс
на http://127.0.0.1:3300

## Как проверить решение

Проверка занимает около минуты и не требует наших аккаунтов.

**Шаг 1. Пайплайн.**

```bash
.venv/bin/python -m pipeline.run --data case/data --out out
```

Ожидаемый вывод — отчёт о загрузке, подобранных порогах и распределении ролей,
последняя строка сообщает о записи трёх выгрузок. Время работы менее 5 минут
(фактически около 10 секунд).

**Шаг 2. Выгрузки.**

```bash
wc -l out/nodes_roles.csv out/clusters.csv out/top_nodes.csv
```

Ожидается: 2249 строк в `nodes_roles.csv` (2248 узлов плюс заголовок),
73 в `clusters.csv`, 31 в `top_nodes.csv`.

**Шаг 3. Любой узел объясним.**

```bash
head -3 out/top_nodes.csv
```

В колонке `why` — обоснование с числами. Возьмите любой `gid` из
`out/nodes_roles.csv`: колонка `evidence` объясняет роль, колонка `rule_id`
называет сработавшее правило, его условие описано в `pipeline/METHOD.md`.

**Шаг 4. Интерфейс.**

```bash
.venv/bin/python server.py --port 3300
```

Откройте http://127.0.0.1:3300 — схема сети. Введите в поиск любой gid из
`out/top_nodes.csv`: узел подсвечивается, открывается досье со связями.

**Шаг 5. Вопрос по графу словами.**

```bash
curl -s -X POST http://127.0.0.1:3300/api/ask \
     -H 'Content-Type: application/json' \
     -d '{"q":"кого смотреть первым"}'
```

Ожидается JSON с полями `answer` (ответ текстом), `nodes` (упомянутые gid),
`source` (откуда взят ответ) и `phrasing` — `правила`, если ключ модели не задан.
Ключ не нужен: без него ответ тот же, только формулировка шаблонная.

Состояние артефактов в любой момент: http://127.0.0.1:3300/api/health

## Ограничения

Перечислены честно — это то, чего решение не делает.

- **Роли — гипотезы для проверки, а не вывод о виновности.** Формулировки в `evidence`
  описывают наблюдаемое поведение счёта, и только его.
- **Размеченных ролей в данных нет**, поэтому точность в привычном смысле не измерима.
  Проверяема обоснованность критериев: каждое правило имеет порог из распределения
  и прослеживается до конкретного узла через `rule_id`.
- **Модель `terminal_p` переносится хуже, чем работает на своей выборке** — AUC 0.64
  на невиданном колене против 0.73 in-sample. Поэтому порог высокий и 358 узлов
  остаются без роли `terminal`, хотя часть из них ею, вероятно, является.
- **Входящие потоки видны не полностью.** Граф собран по исходящим переводам, поэтому
  полный баланс узла недостижим, а у seed-клиентов приток занижен по устройству выгрузки.
- **Дробление ниже 5 000 ₸ невидимо** — такие транзакции в выгрузку не попали.
- **Только внутрибанковские переводы за один месяц.** Выводы за пределы июля 2026
  и за пределы одного банка не переносятся.
- **Нет аутентификации и разграничения прав** — это демонстрационный прототип,
  а не промышленное развёртывание в контуре банка.
- **Работа на графе в миллион узлов не проверялась.** Что изменится в подходе при таком
  росте, описано текстом в `pipeline/METHOD.md`, раздел «Масштабирование».
